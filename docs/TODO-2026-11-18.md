## 一、图片链路（核心，影响带宽成本和加载速度）

### 1.1 现状实测数据

```
图床目录 /var/www/tk-product-automation/
  products/    4,277 张  2,733 MB  平均 654 KB/张   ← 成品库
  auto-temp/   6,059 张  2,857 MB  平均 483 KB/张   ← 临时库（14天自动删）
```

| 格式 | 数量 | 说明 |
| --- | --- | --- |
| JPG | 3,192 | 正常 |
| **PNG** | **1,067** | 商品照片存成 PNG，最大单张 3.8 MB |
| WebP | 18 | 少量 |

| 大小区间 | 数量 |
| --- | --- |
| > 1 MB | **1,053 张**（全是 PNG） |
| 200 KB ~ 1 MB | **0 张** |
| < 50 KB | 88 张 |

**结论：体积两极分化，要么是几十 KB 的小图，要么是几 MB 的 PNG 大图。**

### 1.2 三个根因

**根因 1：PNG 当照片存**
- PNG 是无损格式，为截图/图标设计，不是为照片
- 同一张 1000×1000 商品图：PNG 3.8 MB vs JPG 180 KB，差 21 倍
- 代码里 `image_upload.image_type()` 只按魔数判类型，**不做格式转换**

**根因 2：没有缩略图，列表页加载原图**
- `ProductCard.tsx` 用 `product.image`（= `images[0]` 原图）
- 列表卡片显示 200×200，却加载 654 KB 原图
- 一页 20 件 = 13 MB 流量

**根因 3：nginx 没配 Cache-Control**
- `RemoteImage.tsx` 只有 `loading="lazy"`，没有前端缓存
- 靠 Chromium 的 HTTP 缓存，但服务器没给 `Cache-Control`，缓存效果极差
- 结果：每次刷新页面，图大概率重新下载

### 1.3 要做：入库时统一转 JPEG + 生成缩略图

**改哪个文件**：`server/services/image_upload.py` → `promote_to_product_zone()`

**为什么在这里**：
```
自动化翻译 → auto-temp/（临时，14天删）
       ↓ 入库成品仓时搬文件
promote_to_product_zone()  ← 改这里，只转一次
       ↓
products/（永久）
```
不在翻译前转，因为翻译 API 返回什么格式不确定，可能白转。

**具体改法**：
```python
def promote_to_product_zone(url: str, *, timeout: int = 30) -> str:
    # ... 现有的搬运逻辑 ...

    # 新增：搬运时统一处理
    raw = 读取原文件字节
    converted, is_changed = _to_jpeg(raw)      # PNG/WebP → JPEG q92
    thumb = _make_thumb(converted, 200)        # 生成 200px 缩略图

    # 存原图到 products/<hash>.jpg
    # 存缩略图到 products/thumbs/<hash>.jpg
    # 删除 auto-temp 原文件
```

**`_to_jpeg` 实现要点**：
```python
1. 已经是 JPEG 的图 → 原样返回（不重复压缩，避免二次损失）
2. PNG/WebP → 转 JPEG quality=92
3. 带 alpha 通道（RGBA/LA/P+transparency）→ 先合成白底再转
   （否则透明区域会变黑，商品图背景就毁了）
4. 转换失败（Pillow 没装/图损坏/转完更大）→ 保留原格式，不阻断入库
```

**`_make_thumb` 实现要点**：
```python
1. 用 LANCZOS 重采样（质量最好）
2. 等比缩放到最长边 200px
3. JPEG quality=82（缩略图不需要太高）
4. 同样处理 alpha → 白底
```

**目录结构**（缩略图放子目录）：
```
products/
├── abc123def456.jpg          原图（654 KB）
├── 789xyz.jpg                PNG 转来的原图
└── thumbs/
    ├── abc123def456.jpg      缩略图（30 KB）
    └── 789xyz.jpg
```

**为什么放子目录而不是另建顶级目录**：
- 同一个公开前缀，`AOHUANG_IMAGE_PRODUCT_BASE` 不用改两套
- 清理/备份脚本路径统一
- CDN 可以按 `*/thumbs/*` 单独设规则

**依赖**：`server/requirements.txt` 加 `Pillow>=10.0`（现在没有）。
**注意**：`image_service.py` 已经在用 Pillow（`_shrink` 函数），但没写进 requirements——说明服务器上装过但没固化，要补。

**验收标准**：
- 入库一张 PNG，products/ 里出现 .jpg 原图 + thumbs/ 里出现 200px 缩略图
- 原图尺寸不变（只转格式）
- 带透明的 PNG 转完背景是白的，不是黑的
- auto-temp 里对应的原文件已删除
- 转换失败时原文件还在，商品仍能入库

### 1.4 要做：翻译阶段降流量

**改哪个文件**：`server/services/image_service.py` 顶部常量

**为什么**：翻译单张图要往返 4 次：
```
① 从 1688/妙手下载原图       650 KB
② 上传到翻译 API             650 KB  ← 服务器上行
③ 翻译 API 返回结果          650 KB  ← 服务器下行
④ 上传到图床 auto-temp/      650 KB  ← 服务器上行
                    单张合计 ≈ 2.6 MB
```
一件商品 7 张主图 = **18 MB**；如果是 3.8 MB 的 PNG，**一件 100+ MB**。

**怎么改**：
```python
# server/services/image_service.py 第 296-298 行
SHRINK_LIMIT   = 2 * 1024 * 1024   →  500 * 1024    # 2MB → 500KB
SHRINK_MAX_SIDE = 1600            →  1200          # 最大边
SHRINK_QUALITY  = 85              →  85（不动）
```

**为什么这样改安全**：
- 翻译是识别图片里的文字，1200px 足够
- `_shrink` 已有完整保护：Pillow 没装、图坏了、压完更大，一律原样返回
- 不改变"翻译返回什么格式存什么格式"的逻辑

**验收标准**：
- 翻译一件商品，看日志确认上传的图变小了
- 翻译结果质量没下降（人工看几张）
- 大图（>500KB）触发压缩，小图不触发

### 1.5 ✅ 已确认：nginx 缓存头（本来就有，不用改）

**改哪里**：服务器 nginx 站点配置（`/etc/nginx/sites-available/` 或 `conf.d/`）

**怎么改**：
```nginx
location ~* ^/tk-product-automation/.*\.(jpg|jpeg|png|webp)$ {
    expires 365d;
    add_header Cache-Control "public, immutable";
    access_log off;
}
```

**为什么安全**：
- 图片文件名是内容哈希（`image_store.py` 用 `sha256(raw)[:32]`），内容变了 URL 必变
- 所以可以放心用 `immutable`（永不复验）

**验收标准**：
```bash
curl -I https://aohuang888.com/tk-product-automation/products/<某张图>.jpg
# 应看到：Cache-Control: public, immutable
#        Expires: <一年后>
```

**效果**：用户第二次看同一张图完全不回源，服务器带宽省掉重复访问。

## 七、每项做完的自检方式

### 图片相关
- [ ] 转换后图能打开，无损坏（PIL 校验 `image.verify()`）
- [ ] 尺寸未变（只转格式，不缩尺寸）
- [ ] 透明图合成白底后背景是白的
- [ ] 缩略图确实是 200px，原图字节没变（md5 对比）
- [ ] 前端列表 Network 里请求的是 `thumbs/`
- [ ] 详情页请求的是原图
- [ ] 发布到妙手用的还是原图（读回 payload 里的 imgUrls）
- [ ] 批量脚本重跑不重复转换
- [ ] nginx `curl -I` 能看到 Cache-Control
