## 一、「载体流程改了？多了两步？」

**没改流程，没多步骤。** 我加的那一步插在**原来就存在的两个动作之间**。

### 改之前的实际顺序（代码里的真实现状）

```
publish_service.py:1508-1522
  ① carrier_service.collect_carriers(...)      ← 从公共箱挑一件 → 复制 N 份到店铺采集箱
  ② carrier_service.fill_carriers(...)         ← 用成品数据覆盖每一份
```

### 改之后

```
  ① carrier_service.collect_carriers(...)
       └─ 内部：挑到公共箱某件后、复制之前，多一次 edit_common_collect_box_detail
                （改 sourceList = 这条商品的真实货源）
  ② carrier_service.fill_carriers(...)         ← 完全没动
```

**没有新增「先导入采集箱再处理」这种来回。** 你担心的「先在采集箱处理 1688 链接，
后面再导入采集箱再处理」不存在 —— 采集箱里的商品本来就是载体，我是在它被复制
到店铺之前，把它的货源字段改对。

### 为什么必须插在「复制之前」而不是「写入之后」

实测过，只有这个位置有效：

| 位置 | 能否改货源 |
|---|---|
| 公共采集箱（复制之前） | ✅ 能（回读确认） |
| 店铺采集箱（复制之后、写入时） | ❌ 不能（`save_shop` 返回 success 但回读 null） |

所以顺序不能反。这是因为店铺接口静默忽略 `sourceList`，不是我的选择。

### 新增的耗时

每次覆盖 = 1 次 read + 1 次 edit + 1 次 verify-read，**约 1.5 秒**。
在 0.90 秒节流下，50 件一批多约 **75 秒**。

但只有**商品自己带了货源**时才会做。现在 178 件存量都没链接，
所以**这次改动对当前发布没有任何额外耗时** —— 等于零影响。

## 二、「有效性检查到底有没有用」

**有用，但对你现在的 178 件存量商品没用** —— 因为它们没有链接可检。

### 能做什么（实测）

刚从生产公共箱拿真实 offer 验的：

```
=== 真实存在的 offer ===
717267894593   → verified   株洲夏季透气耐磨男鞋…
1006677085598  → verified   棉鞋2026新款冬季加绒…
980434711914   → verified   男鞋2026新款春季…

=== 乱造的 offer ===
999999999999   → unknown    妙手采集箱里没有该货源，无法确认（不代表失效）
888888888888   → unknown    同上
```

**真链接能判 verified 并带回标题，假链接判 unknown。** 这就是它的用处：
补录链接后点「检查有效性」，能确认这条链接在妙手侧确实对应一件真实商品。

### 存量 178 件的实测结果

```
ready 且未删除: 178
payload 里有 sourceUrl 的: 0
抽样 8 件本地检查: {'missing': 8}
```

**全部是 `missing`（未记录货源）** —— 没有可检的东西。所以顺序是：
**先补录 → 再检查**。

### 为什么不能做得更强

想直接请求 1688 判死活，实测不行：

```
offer 717267894593（真实存在）: HTTP 200, len 2739
offer 999999999999（乱造）    : HTTP 200, len 2739   ← 完全相同的字节
```

两者都是 `_____tmd_____` 反爬壳页。**从服务器侧 HTTP 无法区分死活。**

妙手自己也不校验，官方原话（你截图那条）：
> 不存在的链接也会 success 并采到无关的真实商品。

所以现在的判据只能是「妙手采集箱里有没有过这个 offer」。
搜到 = 可信；搜不到 = 无法确认（**不敢判死**，怕你误删好链接）。

## 三、「静默覆盖 + 自动重启是自动读取当前安装位置覆盖、去掉旧版、再重启吗」

**是。三步都做了，但每步的实现细节决定了成败。**

### 完整流程

```
用户关软件
   ↓ before-quit 检测到 auto-apply.json 标记
powershell（隐藏窗口，detached）
   ↓ 等 800ms —— 让本进程退干净，否则 exe 被占用装不上
   ↓ 读快捷方式 → 拿到安装目录里的 AohuangShangpin.exe
Start-Process setup.exe /S /NOCANCEL -Wait     ← 静默安装
   ↓ Inno 的 UsePreviousAppDir=yes → 装回上次的目录（不是默认目录）
   ↓ [InstallDelete] 段清掉旧文件
   ↓ [Run] 段启动新版本（我已去掉 skipifsilent）
   ↓ 等 3 秒（setup 返回时 exe 可能还没落完盘）
   ↓ Get-Process 判重 —— Inno 已经启动了就不再启动，避免两个窗口
   ↓ 清理 updates 目录里的历史安装包
用户看到的：点了更新，软件重开就是新版
```

### 「自动读取当前安装位置」怎么实现的

三个机制叠加，缺一不可：

| 机制 | 作用 |
|---|---|
| `UsePreviousAppDir=yes` | Inno 读注册表 `InstallLocation` 决定装哪 |
| `DisableDirPage=yes` | 静默时不弹目录选择框 |
| 重启目标读快捷方式 | 安装器把快捷方式指到它实际装的目录，读它比猜路径可靠 |

**这一条昨天我操作失误了，必须说明：**

我清理 0.1.21 残留注册表时，把 `{8F3A2C41-...}_is1` 整个键删了 —— 而
**那个键正是 Inno 记录的安装路径**。删掉后 `UsePreviousAppDir` 无从读取，
下次安装会装到默认的 `%LOCALAPPDATA%\Programs\奥皇上品`，而旧目录 `D:\软件\奥皇上品`
还在 → 变成两份。

已恢复：

```
InnoSetupVersion : 6.2.2 (u)
InstallLocation  : D:\软件\奥皇上品\
DisplayVersion   : 0.1.30
UninstallString  : "D:\软件\奥皇上品\unins000.exe"
```

### 快捷方式会不会指向新版

`setup.iss` 里用 `{app}` 动态展开：

```ini
Name: "{userdesktop}\{#MyAppName}"; Filename: "{app}\{#MyAppExeName}"; Parameters: "--no-sandbox"
```

装到同一目录时，快捷方式指向的就是那个目录里的 exe → **自动是最新版**。

实测当前快捷方式：
```
Desktop\奥皇上品.lnk → D:\软件\奥皇上品\AohuangShangpin.exe --no-sandbox
```

### 「去掉旧版本」

两层：

1. Inno 的 `[InstallDelete]` 段清掉旧文件
2. 我的脚本额外清 `userData\updates` 里的历史安装包（Inno 管不到那里，
   不清就每更新一次多留一个 77MB 的 exe）

注册表那套 0.1.21 残留（旧 Inno AppId）已删掉 —— 这是真正的「旧版本清理」，
之前一直没做干净。

## 四、Cloudflare CDN 怎么弄

### 你现在只需要在 Dashboard 做两件事

**① 给 version.json 加 Bypass 规则（安全底线，必须做）**

```
Cloudflare Dashboard → 选 aohuang888.com
→ Caching → Cache Rules → Create rule
    Rule name: Bypass version manifest
    When incoming requests match:
        URI Path  equals  /miaoshou-downloads/version.json
    Then:
        Cache eligibility: Bypass cache
→ Deploy
```

**为什么必须做**：`version.json` 是「有没有新版本」的唯一判据。它一旦被缓存，
就会出现「发了新版但用户永远检查不到」—— 而且后台看着一切正常，极难发现。

源站已经给了 `no-store`，这条是在 CDN 层再加一道保险。

**② 别把图片站带进 CDN**

`/tk-product-automation/` 必须继续直连（翻译和采集侧在大陆，走 CDN 更慢，
之前实测确认过）。做法二选一：

- 简单：Cache Rule 里给它设 Bypass
- 更干净：给下载单独一个子域名
  ```
  download.aohuang888.com  → CNAME  aohuang888.com
  ```
  只服务 `/miaoshou-downloads/`，图片站完全不受影响

### 我这边已经做好的（服务器侧）

```
安装包:      cache-control: public, max-age=31536000, immutable
version.json: cache-control: no-store
```

顺手删掉了过时的 `latest-Setup.exe` 软链接（还指向 0.1.23）。

### 不要开的 CF 功能

| 功能 | 为什么不开 |
|---|---|
| Rocket Loader | 会改 HTML 里的 script，`miaoshou-platform` 是 SPA，容易坏 |
| Auto Minify | 同上 |
| Always Online | 源站挂了返回旧缓存，用户以为「服务正常但功能异常」 |

只开 CDN 加速 + 缓存规则。

## 五、「换流量大的服务器，下载会变快吗」

**会快一些，但不是线性关系 —— 而且我上一轮已经用实测证明了瓶颈不在这里。**

### 上一轮的实测数据（同一台机器、同一时段）

| 目标 | 速度 |
|---|---|
| 自家服务器（跨境直连） | 200 KB/s ~ 1.4 MB/s（波动剧烈） |
| **Cloudflare 香港节点** | **3 ~ 9 MB/s（稳定）** |
| 阿里云国内节点 | 3 KB/s |
| 服务器自己的回环 | 13 MB/s |

同时段的服务器状态：

```
TCP 重传率 14.9%（32,440,467 发出 / 4,835,126 重传）
CPU 98% 空闲（3 个并发下载时）
CPU steal 0%
load average 0.12
单连接 363 KB/s（74MB 用了 205 秒）
4 个并发 = 1.7 MB/s
```

**结论：瓶颈是跨境回程线路的丢包/重传，不是 CPU、不是内存、不是带宽。**

### 所以换服务器要看什么

| 该看 | 不该看 |
|---|---|
| 回程线路（CN2 GIA / 优化回国） | CPU 核数 |
| 重传率（< 3% 才算好） | 内存大小 |
| 是否独享带宽 | 标称带宽数字 |

「流量大的服务器」如果还是普通国际线路，重传率一样高，**下载不会明显变快**。

### 但换 CDN 一定比换服务器便宜且有效

```
现在：74MB → 205 秒
CDN 后：74MB → 约 10~25 秒（按 CF 香港实测 3~9 MB/s）
```

**CDN 是叠加在上面两种方案之上的**，不管是现在的服务器还是以后换的，
走 CDN 都能拿到这个速度。所以顺序应该是：

1. **先开 CDN**（免费、立刻见效，你只需在 Dashboard 点两下）
2. 如果还想换服务器，按「回程线路 + 重传率」选，别按 CPU/内存选
