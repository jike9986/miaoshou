# 批量认领、定时发布和载体读回验收

日期：2026-11-03。范围为仓库认领、共享妙手 key 的用户隔离、定时发布的提交与回执，以及保存后核验。全部使用独立临时 SQLite 和模拟妙手网络边界，没有操作真实商品、真实上架或创建线上定时任务。

## 已完成的验证

- 分别执行 200、500、1000 件成品的完整服务链：`claim_job_service.run` → `publish_service.publish` → `collect_carriers` → `fill_carriers` → 保存读回。已有公共采集箱商品时，每次批量复制 100 份，不重新采集 1688，不逐件复制；每件均覆盖成品标题、重量、价格。
- 任务完成后重新打开数据库会话，检查总进度、逐件结果、已认领状态。共用同一妙手 key 的第二软件用户看不到第一用户的任务、认领或发布台账。
- 两名用户对同一共享成品分别建立定时发布任务。08:59 不执行，09:00 分别复制草稿、套用真实定价算法、保存读回并提交，09:01 不重复提交；不同用户的载体和台账独立。
- 提交后显示“待回执”，不会显示“已成功”。通过真实回执刷新逻辑，第一用户成功不会更新第二用户；第二用户失败会更新其对应历史。最终失败也不会触发当天自动重发。
- 模拟上游已收到发布请求、响应超时：由提交前已持久化的精确批次台账恢复“待回执”，数据库重开后仍可核对，不自动重新发商品。
- 同一个发布台账 ID 后续换到新批次时，仅更新对应批次历史；账号和操作人不匹配时拒绝更新。
- 保存后读回超时、空数据、异常结构或比较器异常，全部阻断发布。读回售价、采购价或类目与本次提交不一致，也全部阻断，且没有正式发布调用或成功台账。

## 修复内容

1. 定时任务区分最终成功、待回执与失败，按本次批次 ID 和发布台账 ID 精确接收最终结果；前端最近结果、执行提示和历史表均显示待回执数量。
2. 历史摘要不再直接截断 JSON 字符串，避免丢失或损坏回执关联数据。
3. 载体保存读回失败不再返回空差异。以本次提交的成品覆盖数据为核验目标，校验适配后的类目、模板售价和采购价；不再忽略价格差异或用种子商品的旧价格判断成品。

## 实际边界

- 200/500/1000 证明的是本地真实服务链在确定的模拟上游下正确处理数量、覆盖、持久化与隔离；没有把模拟验收表述成真实平台一次性处理 1000 件的速度或限流保证。
- 最终发布结果需要在“发布记录”回源刷新，随后定时摘要和历史会同步。当前没有新增后台持续回执轮询。
- 重量、尺寸等仅验证成品保存值与读回一致，不代表这些值已与实物核实。
